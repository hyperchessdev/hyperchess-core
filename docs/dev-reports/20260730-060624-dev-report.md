## What was done

### Issue B — castling never occurs (root cause found, fixed, 100% confirmed)

`crates/hyperchess-rules/src/core/piece_identity.rs`'s `START_HFEN_I` constant — the exact
string `Board::start_pos()` parses via `Board::from_hfen` — encoded the HFEN castling field as
`-` instead of `KQkq`:

```
"12/abcdefghijkl/mnopqrstuvwx/12/12/12/12/12/12/MNOPQRSTUVWX/ABCDEFGHIJKL/12 w - - 0 1"
```

`Board::from_hfen` (`crates/hyperchess-rules/src/board/mod.rs:102`) sets
`board.state.castling = CastleRights::from_hfen(&data.castling)` directly from that field —
there is no fallback to `CastleRights::default()` (which is `ALL`). Since
`CastleRights::update_for_move` (`crates/hyperchess-rules/src/board/castle_rights.rs:83`) only
ever *clears* bits and nothing in the codebase ever *sets* them, every game starting from
`Board::start_pos()` began with **zero** castling rights from move one, for the entire game —
deterministic, not probabilistic. This explains "0 castling in 500k games" exactly; no random
seed, engine choice, or skill level could ever produce a castling move.

Corroborating evidence that this was an unintended data bug, not a design choice: the JS/TS
layer's own hand-written starting-position literals already had the correct castling field —
`packages/board/src/web-component/hyperchess-board.ts:22` and every fixture in
`packages/store/src/__tests__/game-store.test.ts` use `w KQkq - 0 1`. Only the canonical Rust
constant was wrong.

**Fix:** changed `START_HFEN_I`'s castling field from `-` to `KQkq`
(`crates/hyperchess-rules/src/core/piece_identity.rs:19-27`). Two test fixtures had baked in
the wrong value and needed updating as expected, correct fallout of the fix (not new bugs):
- `crates/hyperchess-rules/src/board/hfen.rs::test_parse_start_hfen` — asserted
  `data.castling == "-"`; now asserts `"KQkq"`.
- `crates/hyperchess-driver/src/cli/game.rs::test_save_hfeni_and_hpgni` — asserted the first
  line of an exported `.hfeni` file (which is `Board::start_pos().get_hfen()`) contained
  `"w - -"`; now asserts `"w KQkq -"`.

No other test needed changes — in particular no perft/move-count regressions, because at the
literal starting position castling is still blocked by the intervening knight/bishop regardless
of rights (the bug only ever mattered once a real game developed far enough to clear the path,
which is exactly the phase where it silently never became available).

### Issue A — grandmaster MCTS won't force mate in a won endgame (partial fix, verified improvement; full fix out of scope)

**Root cause (confirmed via code inspection + empirical repro):** `hyperchess-search::mcts`'s
CPU rollout (`mcts_bounded`, `crates/hyperchess-search/src/mcts.rs`) scores every non-terminal
leaf via `evaluate(&leaf_board)` clamped to ±3000cp → ±1.0, with **no** full playout to an
actual terminal state (MCTS here expands exactly one new node per simulation; the "rollout" is
a single static-eval call, not random/tactical play-out). Once one side is hugely materially
ahead, essentially every legal reply keeps that same clamped near-max score, so UCB1 selection
has no gradient distinguishing "this move converges on mate" from "this move shuffles
aimlessly" — a known, textbook weakness of static-eval-rollout MCTS without a mop-up/mating-
technique evaluation term (Stockfish and similar engines carry an explicit one for exactly this
class of ending; this evaluator had none). Compounding this: Black having no material left
means White is the only side that can ever reset `rule50` (via a pawn push), so as long as
White retains pawns, the internal 224-halfmove no-progress draw can be deferred indefinitely
while the game shuffles — a real game can run far past that safety net if whatever external
`--max-moves`/ply-cap configuration was in use was also set high.

Simplified synthetic endgames (K+Q+R+2P vs. K on an open board; a full 14-piece back rank vs. a
cornered lone king) actually converged to checkmate quickly (13 and 151 plies) even *before*
any fix — the failure mode only reproduced reliably in an adversarial-but-realistic setup: full
starting material scattered across the board with the defending king starting on an open edge
square rather than a true corner. That case did not reach checkmate within an 800-ply budget.

**Fix implemented:** added `mating_technique_bonus_cp` to
`crates/hyperchess-search/src/mcts.rs`, folded into the CPU leaf score
(`leaf_score`) before the existing clamp. Gated to positions where the defending side has under
~400cp of material (so ordinary middlegame/endgame play is untouched), it rewards (a) driving
the defending king away from the board centre using a **Manhattan-style** distance
(`edge_distance`, sum of the two axis distances) and (b) reducing the distance between the two
kings. The Manhattan choice matters: an earlier Chebyshev/`max`-based version saturates the
instant *either* axis alone reaches the rim, so a king stuck on a mid-edge square (free to
roam the full width of that edge) scores identically to a true corner — giving no further
gradient to push it the rest of the way in. Switching to the sum fixed exactly this: the same
800-ply-unconverged adversarial position above reached checkmate at ply 713 with the corrected
metric.

**This is a real, verified improvement, not a complete fix.** 700+ plies is still a long game
for a position that is trivially won on paper. A full fix would need either shallow tactical
lookahead inside the MCTS rollout (instead of a single static-eval call) or a trained value
network (AlphaZero-style) — both out of scope for this session. The GPU/CUDA MCTS path
(`hyperchess-search-cuda`, used by `cuda_mcts` in `hyperchess-cuda-eve.sh`) uses an entirely
separate kernel-based evaluator and was **not** touched; the same class of weakness likely
applies there and would need a parallel fix.

New unit tests added (`crates/hyperchess-search/src/mcts.rs`, `mod tests`):
`mating_technique_bonus_is_zero_outside_bare_king_endings`,
`mating_technique_bonus_rewards_cornering_the_bare_king`,
`mating_technique_bonus_reflects_side_to_move_in_leaf_score`.

## Decisions of record

1. **`START_HFEN_I`'s castling field is now `KQkq`, not `-`.** This is the single source of
   truth for `Board::start_pos()` (via the `START_HFEN` alias in `core/masks.rs`) — every
   consumer (CLI, live-stream server, `hyperchess-sim`, WASM) inherits this automatically since
   they all depend on `hyperchess-rules` via path. Do not revert this without understanding it
   was a bug, not an intentional no-castling design (the JS/TS layer's own literals already
   expected `KQkq`).
2. **The MCTS mating-technique bonus is CPU-only** (`mcts_bounded`'s leaf scoring), not applied
   to `mcts_with_eval`/`mcts_with_eval_bounded`'s external-evaluator path (used by the CUDA/GPU
   `cuda_mcts` engine). This was a deliberate scoping decision to keep the fix small and
   testable without touching CUDA kernel code this session couldn't verify. The GPU path has
   the same class of weakness and needs a parallel (likely kernel-level) fix later.
3. **`hyperchess-sim`'s pre-existing build failure and `live-stream-gameplay`'s unused
   `search_time_cap_ms` were both left unfixed**, deliberately, as out of scope for this
   session's ask — see Open items.
