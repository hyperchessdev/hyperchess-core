## What was done

**Diagnosis.** `oc get pods -n kyrpy-server` showed `hyperchess-live-stream`'s current pod
(`hyperchess-live-stream-79b5d56984-cdszv`) was actually stable — 0 restarts, both containers
(`server`, `broadcast`) running 19h+ with no `lastState` history. The real crash source was
**`hyperchess-msrv-engine`** — the engine microservice live-stream calls for `/move/best` — whose
two pods each showed 2 container restarts in 24h and recurring `Unhealthy` events (`Readiness
probe failed` / `Liveness probe failed: context deadline exceeded`) as recently as ~3h before
this session started, not yet escalated into a fresh restart but trending that way. (Separately,
`hyperchess-live-stream`'s ReplicaSet history showed 17 revisions churned in ~30h — high, but
explained by prior sessions' repeated manual redeploys, not crashing; not investigated further as
it wasn't the actual symptom.)

**Root cause**, found in `hyrperchess-core/crates/hyperchess-driver/src/api/handlers.rs`:
`best_move`'s handler is an `async fn` with **zero `.await` points** — the alpha-beta/MCTS search
(`TimedSearcher`, `mcts_bounded`, `make_searcher`, all synchronous/CPU-bound Rust) ran directly
inline. Since the handler never yields, Tokio's cooperative scheduler can't preempt it: whatever
worker thread picks up a `best_move` request is held hostage for the entire search duration (up
to the request's `movetime_ms`, or however long depth-N search takes). Under concurrent request
load, this could starve `/health` long enough that the Istio-proxied liveness/readiness probes
(`context deadline exceeded`, 3s timeout) failed repeatedly and eventually crossed the liveness
failure threshold, so kubelet killed the container mid-game — the actual "pod crash" the user was
seeing (surfacing to end users as live-stream disruption, even though live-stream's own pod never
restarted).

**Fix**: moved the search onto `tokio::task::spawn_blocking` so it runs on Tokio's dedicated
blocking-thread pool, leaving async worker threads free to serve `/health` (and other routes)
regardless of in-flight search duration. `eval_cp` is computed inside the same blocking closure
(no extra clone of `Board` needed). `algorithm` changed from `&str` (borrowed from the request)
to an owned `String` so it can move into the `'static` closure.

**Regression test added** (`health_stays_responsive_while_a_search_is_in_flight` in
`crates/hyperchess-driver/tests/api.rs`): a same-runtime `router().oneshot()` test *cannot* catch
this class of bug — if the measurement (the `/health` call, its timeout, its wakeup) shares the
same runtime that's starved, the measurement stalls right along with it and passes either way
regardless of whether the fix is present (confirmed this empirically — an earlier draft of this
test using `oneshot()` + `tokio::spawn` passed even against the unfixed handler). The test instead
runs the real server via `axum::serve` on a **dedicated single-worker-thread Tokio runtime on its
own OS thread**, then probes it over a **real TCP socket** from the test's own independent thread
with a hard `set_read_timeout` — reproducing what kubelet's probe actually experiences.
